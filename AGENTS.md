# Instructions for AI agents

This repository is **agent-fleet**: it lets one AI agent (the *orchestrator*, usually Claude Code) manage Codex agents on many computers. Read `README.md` first for the architecture. This file tells you how to **set it up for a user** and how to **work on the code**.

## Setting it up for a user

Ask the user which role this computer should have; it can have both:

- **Worker**: a computer whose agents do the work, such as video editing, browser tasks or desktop apps.
- **Orchestrator**: the computer where the user talks to Claude Code and manages the fleet.

### Worker (Windows)

1. Confirm the user wants this computer controlled by agents. Explain **`-FullAccess`**: sub-agents run without a sandbox and every permission prompt is auto-approved. They can then operate the desktop, browsers and apps, but also do anything else on the machine. Use it only if the user agrees. Without it, sub-agents can only write their own working folder.
2. From the repo root, run: `powershell -NoProfile -ExecutionPolicy Bypass -File .\install-worker.ps1 [-FullAccess] -Description "<what this computer is for>"`
   It installs missing Node.js / Python / Tailscale (via winget) and the Codex CLI. It also deploys the dispatcher, creates the computer's main agent ("主agent export") and adds autostart at logon.
3. Two steps need the human, and you cannot do them: **signing in to Tailscale** (the tray app, or `tailscale up`) and **signing in to Codex** (`codex login`). If the script warns about either, ask the user to do it, then re-run the script.
   The agents' working area is `%USERPROFILE%\AgentFleet\` (`main-agent\`, `AgentFleet-其他\` or `AgentFleet-Other\`, `shared\`); pass `-Workspace <path>` to put it elsewhere, e.g. on a bigger disk for video work.
4. The script writes `%LOCALAPPDATA%\agent-fleet\connection.json`. It contains this computer's **token**: never print it, paste it into chat, or commit it. Tell the user to copy the file to their orchestrator computer.

### Worker (macOS)

Same flow, through `bash install-worker.sh [--connectivity local|tailscale|lan] [--full-access] [--language zh|en] --description "<what this computer is for>"` (run as the normal user, never with sudo). It uses Homebrew for missing Node.js/Tailscale, keeps data in `~/Library/Application Support/agent-fleet/`, and adds a LaunchAgent (`com.agentfleet.worker`) for autostart. The same two human steps apply (Tailscale and `codex login`). With full access, the owner must also grant Accessibility and Screen Recording in System Settings; you cannot do that. `worker/start.sh`, `stop.sh` and `pair.sh` control the service.

### Orchestrator

1. Preferred: in Claude Code, `/plugin marketplace add cxfydhcg/agent-fleet`, then install the `agent-fleet` plugin. The skill is `/agent-fleet:call-agent`.
   In Codex: `codex plugin marketplace add cxfydhcg/agent-fleet`, then `codex plugin add agent-fleet@agent-fleet`, and start a new chat.
2. For each worker: preferably pair with the code the worker shows (`fleet.mjs discover`, then `fleet.mjs pair <code>`, or `pair <IP> <code>`); otherwise `node <skill folder>/fleet.mjs add-computer <path to its connection.json>`. If the orchestrator is also a worker, add `--local=1`. Afterwards the user can delete the `connection.json` file.
3. Verify with `node <skill folder>/fleet.mjs overview`. Then send a harmless message, e.g. `/call-agent 【<computer>】 reply with "ok", don't use tools`.

### Rules while helping

- Never print, log or commit tokens (`token.txt`, `connection.json`, `.codex/config.toml` in the main agent workspace, `~/.agent-fleet/tokens/`).
- Don't open sessions that agents are using in the Codex desktop app. The app locks every session it has opened until Codex fully exits. To watch, open the fleet board on the orchestrator (`fleet.mjs dashboard`; it covers every computer and needs no token in the page), or one computer's own `/dashboard` (port 8766 over Tailscale, or 8765 locally).
- Ask before deleting data, publishing anything, or changing account settings on the user's behalf.

## Working on the code

- The unified plugin is in `plugin/`; read `PLUGINS.md`. Its setup skill lets the user choose orchestrator, worker or both, and it packages skills for Codex and Claude Code. Run `python tools/build_plugins.py` after shared runtime/client edits to rebuild the bundled worker runtime and fleet client. Only the unified plugin is maintained; do not retain the former split role packages.
- Until the first GitHub tag is published, backward compatibility is not required: do not add compatibility shims or automatic migrations; require the current data and protocol formats. After the first tag, decide compatibility requirements based on actual users and release needs rather than treating this as a permanent ban.
- `worker/claude_executor.py` adapts Claude Code print-mode sessions. Claude desktop only lists sessions in its own index, so after a new task's first successful turn the executor imports the session with the `claude://resume?session=<id>` deep link (config `claude_desktop_import`: `new` default, `off`). Importing opens it, so the app keeps a live `claude-desktop` process for it (registered in `~/.claude/sessions/*.json`); background turns still `--resume` the same session, which the app shows after a restart. Only while that process reports `status: busy` (the owner is working in it) does `desktop_holds` make the next turn run `--resume <id> --fork-session` (recorded as `forked_from_thread_id`), leaving the owner's copy untouched. It uses per-turn MCP task headers for callback attribution, preserves session IDs, and defaults to restricted file tools. Claude's tool permissions are not a Windows OS sandbox. Never add permission bypass flags unless the owner chose full access.
- Run the dispatcher and Claude adapter tests plus `tests/test_plugins.py`. Claude fixtures never call a model. Validate each plugin and the marketplace with `claude plugin validate`; source distribution must exclude machine data and credentials.

- `worker/server.py`: the dispatcher (FastMCP over Streamable HTTP; runs Codex through `codex app-server`). Per-computer config is passed with `--config`; nothing machine-specific belongs in the repo.
- Quota guard: before each app-server turn the dispatcher calls `account/rateLimits/read`; if the 5-hour (`primary`) or weekly (`secondary`) window is at `quota_guard_threshold` percent (default 100), the job goes back to `queued` and the whole queue waits for the reset. Config keys `quota_guard` and `quota_guard_threshold` are described in `README.md`. Errors and unknown answers must never block.
- `worker/test_dispatcher.py`: run it from `worker/` with `python -m unittest test_dispatcher.py`. Keep it passing and add tests for new behavior. Tests use a fake app-server and never call a real model.
- `worker/tools/codex_app_folder.py`: optional, stdlib-only helper that files the dispatcher's sessions into a Codex desktop app sidebar folder by editing the app's internal `~/.codex/.codex-global-state.json` (undocumented; may break with app updates). Keep its JSON transform in `add_to_folder` pure so it stays testable. The dispatcher uses the same transform (`sort_into_folders`) when config `codex_app_folders` is on, filing sessions into a main-agent folder and an other-agents folder only while the desktop app is closed. Optional config keys `resident_title_suffix` and `codex_app_folders` are described in `README.md`; `codex_project_id` (unset by default) puts new sessions into that Codex project through the app-server's experimental `projectId`.
- `worker/templates/main-agent/AGENTS.md`: the main agent's instructions; `{{COMPUTER_NAME}}` and `{{WORKSPACE}}` are filled in at install time. `AGENTS.en.md` and `worker-rules.en.md` are the English versions; keep each pair in sync.
- Language: config `language` (`zh`/`en`) picks every user-visible text. In `server.py` such text lives in the `TEXT` table; the dashboard has its own `I18N` table; installers use `T '中文' 'English'`; `fleet.mjs` uses `T(zh, en)`. Add new user-visible strings in both languages.
- Pairing: `/pair/start` (token) opens a 10-minute window with a one-time 8-digit code; `/pair/info` and `/pair/claim` are public only while it is open, and `/pair/claim` returns the connection info (with the token) for the right code once; 5 wrong codes close it. `fleet.mjs discover` / `pair` are the orchestrator side. Never make the token obtainable without the code.
- Orchestrator: a session, not a folder. Setup stores the running Claude Code / Codex session id as `orchestrator_session` in the registry (worker setup does the same in its local-client registry); `fleet.mjs claim-orchestrator` moves it. Only that session reaches main agents and may `discover` / `pair`; other sessions get their own agent in the worker's other folder. The orchestrator creates no workspace and no Codex desktop project; only workers do.
- Windows app sandboxes: the Codex and Claude desktop apps (Microsoft Store) redirect AppData writes into their private storage, and Codex also points `LOCALAPPDATA` there. The worker's data dir is therefore always `%USERPROFILE%\AppData\Localgent-fleet` (never `$env:LOCALAPPDATA`), and `plugin/scripts/windows-outside.mjs` detects the sandbox (`appDataRedirected`) so `setup.mjs` and `start.mjs` run the PowerShell part through WMI outside it (`runOutsideApp`). Keep new Windows paths and launches going through these.
- Desktop sidebar folders, one rule for both engines (`TaskManager.sidebar_side`): the main agent and every session it opened go in AgentFleet (the workspace), sessions others opened directly in AgentFleet-Other (`tasks_dir`). Codex: `sidebar_project` finds (or creates) the app-server project by root and passes `projectId` to `thread/start`, or `thread/metadata/update` on resume, which works while the desktop app is open; the state-file filing remains the fallback for older Codex. Claude desktop groups sessions by their exact working directory, not by parent folder, so `claude_executor.session_cwd` starts a new session in the workspace or `tasks_dir` by that rule; the task's own folder is passed with `--add-dir`, named in the system prompt, and is the only folder a restricted session may edit. A resumed session keeps the `cwd` recorded on its earlier job (or that job's workspace), since `--resume` looks a session up by directory.
- Engine parity: Claude workers match Codex ones. Usage limits: Codex is checked before a turn (`check_quota`); Claude Code reports limits only while running, so a `rate_limit_event` with status `rejected` (or a usage-limit error) before any reply puts the task back in line and `check_claude_quota` holds the queue until `resetsAt`, with the same pause/resume notifications (`QuotaExhausted(engine=...)`). Removed sessions: `removed()` reads Codex's archived/active rollouts, or for Claude the desktop index (`isArchived` in `local_<id>.json`) and `~/.claude/projects` transcripts. Desktop links: `codex://threads/<id>` or `claude://resume?session=<id>`; `open_desktop` and the dashboard handle both. Setup opens nothing in Claude desktop (`desktop.status: automatic`). A session the owner holds in the desktop app continues in a fork for both engines (Codex: `fork_when_busy`, default on; Claude: `desktop_holds`).
- Updating: the `update` skill updates this computer (plugin in each app, then worker setup from the new version) and, from the orchestrator, runs `fleet.mjs update <computer>` per computer: a one-off task (not the main agent) updates the plugin and reruns setup, then the client waits for `/health` to report a new pid and reads `version` (from `service/plugin-version.txt`). Setup reruns open no pairing window unless the install is fresh or connectivity changed.
- Updating a busy worker: setup (Windows `setup-worker.ps1`, macOS `install_mac.py`) no longer refuses or kills a busy service. It deploys the new code and writes `<state_dir>/restart-when-idle`; `TaskManager.restart_loop` relaunches the service (`start_service.py --after-pid`) once no task is queued or running. This is what lets an orchestrator update a worker by asking that worker's own main agent to update the plugin and rerun setup, whose turn keeps the service busy.
- Files: `/api/files?path=` lists and `/api/file?path=` streams (with Range) files under the worker's `shared_dir` and `tasks_dir` only (`output_roots`, `resolve_output_path` in `server.py`; anything resolving outside is refused). `fleet.mjs files` / `fetch` and the fleet board's Files tab use them; the board serves files with a `sandbox` CSP so an opened SVG/HTML cannot script it.
- Names: the session title is the user's (the dispatcher sets it only when the title it wants changes), the management name (`manager_name`) belongs to the orchestrator, and `main_agent_id` (in the service's `profile.json`, created at first setup) is the permanent key the orchestrator maps to. Never route the main agent by name when the id is available.
- `plugin/skills/call-agent/`: the orchestrator skill and its client `fleet.mjs` (Node 18+, no dependencies). `fleet.mjs dashboard` serves the fleet board on 127.0.0.1 only: it embeds each worker's own `/dashboard` and forwards just its read-only `/api/*` reads with the token added server-side, so the page never holds a token. Access needs the one-time key from the printed link (then an HttpOnly cookie), and the Host header must be the loopback address. Test: `node --test tests/test_fleet_dashboard.mjs`.
- Workers run on Windows and macOS. Windows: `install-worker.ps1`, `worker/start.ps1`, `stop.ps1`, `pair.ps1`. macOS: `install-worker.sh` → `worker/install_mac.py`, `worker/service_ctl.py` (start/stop/status; wrapped by `start.sh`, `stop.sh`; `pair.sh`). Keep both installers producing the same config keys and `connection.json` fields, and keep runtime code portable (guard Windows-only calls with `os.name == 'nt'`, macOS with `sys.platform == 'darwin'`). The plugin's `setup.mjs` runs `setup-worker.ps1` on Windows and the Mac installer (deployed to `<workspace>/service`) on macOS.
- PowerShell scripts must run on Windows PowerShell 5.1: no `&&`, `??` or ternaries. Save them as UTF-8 **with BOM**, because they contain Chinese text. Variable names are case-insensitive: a `$Config` parameter would clobber a `$config` variable.
- Validate the plugin with `claude plugin validate .` after changing `.claude-plugin/` or `plugin/`.
